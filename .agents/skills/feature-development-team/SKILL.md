# Feature Development Team

Coordinate four distinct subagents in sequence: financial data specialist, planner, builder, and independent verifier/Jira writer. Finish each handoff before starting its dependent stage; do not run independent overlapping team skills or spawn an additional review team. Reuse these roles for clarification, corrections, and rechecks. The parent owns scope, report updates, and handoffs. Use fresh context (`fork_turns="none"`) and give each role the repository path, applicable AGENTS.md, explicit mode/scope, permitted operations, and completed preceding output. Roles do not spawn more agents. Do not invent successful delegation if unavailable; report the limitation and continue only work actually authorized.

## Mode and authorization

- **Plan only:** assess the requested workspace or feature and produce prioritized, evidence-based improvements with acceptance criteria. The builder supplies implementation/effort estimates without modifying code. The verifier checks feasibility and may publish the selected proposals to Jira. Assessing a workspace is not authorization to implement its entire backlog.
- **Build:** implement the requested feature or a bounded improvement slice aligned with the user's outcome, verify it independently, and ticket unresolved defects or substantive follow-up work. A request to build, implement, fix, or improve functionality authorizes this mode within the named scope. Avoid unrelated redesigns, new providers, or speculative features. If a broad request has several materially different product directions, continue discovery and ask for the decision before implementing dependent work.
- A bare invocation without an outcome defaults to plan only and requests the target workspace/feature; inspect PLAN.md while awaiting clarification. A request to create/edit this skill does not execute a feature run or publish Jira issues.
- Explicit invocation authorizes delegation, local reports, mode-appropriate implementation, and up to five Jira creation attempts. `drafts only` or `do not create tickets` disables Jira writes. `dry run` disables implementation and Jira writes, regardless of a conflicting build phrase. State the resolved mode before work.
- No staging, commits, pushes, deployments, existing Jira modifications, status transitions, assignments, or other external messages unless separately requested. Tests and verification must not consume paid API credits or call live providers.

## Coordinator: establish the run

Read the working tree, applicable instructions, PLAN.md and relevant module boundaries. Preserve unrelated work; identify any existing edits in target files and attribute the team's delta separately. Record baseline commit, initial status, and scoped file hashes/diffs. Do not discard user edits or classify them as team-delivered features.

For a new run, create an unused UTF-8 report at `docs/features/YYYY-MM-DD-<task-slug>-team.md`, using the user's timezone, lowercase hyphen-separated scope, and `-2`, `-3`, etc. on collisions. Its filename stem is the run ID. Resuming interrupted work reopens that original report and run ID, retaining all recorded attempts; creating another report must not reset the same run's budget. If the original ledger cannot be recovered, allow drafts only. Record mode, outcome, scope, acceptance criteria, plan, delivered delta, actual verification, remaining work, Jira drafts/results, and a durable attempt ledger. Exclude generated reports, secrets, caches and dependencies from inspection inputs. Never overwrite past reports.

Jira defaults to `https://bigmeatpete717.atlassian.net`, project `AAFA`; honor an explicitly supplied alternative. Hard cap: five creation attempts for the entire run, lowered by the user's requested limit. No minimum quota. Interrupted, failed, and uncertain attempts consume the same budget.

## Agent 1: financial data specialist

Establish the data evidence needed for the requested outcome before planning or implementation. Remain read-only: no source edits, collection-script execution, live provider/model calls, or Jira writes. For a task unrelated to financial/provider data, return a brief not-applicable handoff rather than inventing data requirements.

For FMP work, consult `fmp_data_reference/context_index.md`, `collection_report.md`, `endpoint_inventory.csv`, and `coverage_matrix.csv`. Filter coverage for the actual requested ticker, route and variant; inspect relevant dictionary entries, observed schemas and exact saved samples. Use `scripts/query_reference.py` or targeted reads rather than loading the entire dictionary. Do not treat workbook examples, another ticker's success, or an observed schema union as confirmed ticker coverage or a provider contract. If the reference is absent or incomplete, identify the gap without fabricating fields or assuming entitlement. For other providers, inspect the existing adapter contracts and recorded/synthetic fixtures, identifying unsupported assumptions.

Return stable data requirement IDs (`D01`, ...), with:

- requested metric/user outcome and normalized security identity;
- API ID, exact route/variant, parameters and reference/sample paths;
- relevant field paths, observed types, null/missing behavior, and known versus inferred definitions;
- units/currency, annual/quarterly/TTM basis, fiscal alignment, data date versus retrieval time, and price-adjustment basis where relevant;
- observed coverage and access restrictions, including successful legacy alternatives without claiming route equivalence or future entitlement;
- proposed existing provider/domain integration, fallback/error behavior and offline fixtures/validation rules;
- unresolved meaning, scaling, freshness, completeness or access questions and their implementation impact.

This handoff is a dated evidence map, not a live data pull or proof that the app already uses an endpoint. Prefer successful task-relevant saved samples and synthetic edge cases for implementation and tests. Live recollection requires separate explicit authorization, remains outside offline verification, and must not run in plan-only/dry-run mode. Record authorized live evidence separately from offline test results. The coordinator saves the handoff in the run report and passes it to the planner, builder and verifier; source requirement changes return to this specialist before dependent implementation proceeds.

## Agent 2: planner

Use the financial specialist's handoff to inspect the requested product surface, existing behavior, tests, current roadmap, and surrounding workflows. Link proposals to applicable D IDs and identify which unresolved data questions block them; do not convert inferred definitions into established facts. Prioritize correctness/provenance, recovery, connected workflows, coverage, performance, then polish and feature breadth per AGENTS.md. Proposals need a concrete user problem and supporting source paths or reproducible workflow observations; distinguish observations from hypotheses.

Return stable item IDs (`P01`, ...), ranked improvements, user outcome, acceptance criteria, affected modules, data/session-state implications, offline verification plan, estimated scope and dependencies. Explain live/missing/partial/stale/failed-data behavior where relevant. Separate selected build scope from follow-up opportunities. Do not claim implementation or measured cost savings from inspection. Read-only source/Jira access only; no implementation or issue creation.

## Agent 3: builder

In plan-only/dry-run mode, evaluate the selected proposals against current architecture and return implementation steps, effort estimates explicitly labeled as estimates, dependency risks, and test suggestions. Make no code or product documentation edits.

In build mode, implement the selected bounded scope using the saved data handoff. Trace relevant changes and fixtures to D IDs; do not silently substitute another endpoint, fiscal basis, currency, ticker or provider. Send new data requirements or contradictory responses back through the coordinator to the specialist. Missing evidence blocks the affected assumption, not independent authorized fixes. Follow AGENTS.md, use relevant focused project skills when useful, keep presentation/providers/domain logic separated, preserve Deep Research V1 when modifying V2, and avoid automatic paid calls. Add/update tests at the lowest useful level and handle the agreed acceptance criteria. Do not touch unrelated user changes or expand scope to fill a ticket quota.

Run focused offline tests and compile/import affected modules with the installed Python 3.11/3.12 environment. Shared infrastructure/routing changes require the full pytest suite. App-level changes require a fresh Streamlit health check and the changed browser interaction when tooling is available; follow the release-check reference for applicable commands. Update README when workflows/setup/navigation change and PLAN.md for meaningful delivery, keeping unmet criteria and actual evidence explicit. Return changed paths, delta, commands/results, dependency/interpreter versions, unverified acceptance criteria and remaining risks. Do not mark a feature done when required checks fail or remain unperformed.

## Agent 4: independent verifier and Jira writer

First verify independently; only then publish eligible tickets. Receive the data handoff as evidence to check, not conclusions to accept: independently inspect relevant coverage, samples and field/period/unit assumptions against the implementation. Report unsupported substitutions or unresolved data requirements. Include applicable D IDs and key data evidence in ticket drafts. In build mode inspect the team's delta against the initial snapshot and relevant existing changes for interactions, without attributing pre-existing edits to this delivery. Check the builder's acceptance criteria and actual evidence; run focused independent offline checks where useful. In plan-only mode validate proposal evidence, feasibility and acceptance criteria without claiming tests of unbuilt features. Remain read-only for implementation files in all modes.

Return severity-ranked findings with stable IDs (`F01`, ...), affected path/line, trigger, impact, observed versus inferred evidence, correction direction and proposed regression checks. Distinguish pre-existing issues from introduced regressions. Unsupported/speculative items are report-only, not tickets. Merge shared root causes and retain IDs. Rank by concrete impact/evidence, prioritizing financial correctness, security, recovery and useful workflows. Enhancement proposals are labeled proposals, not defects.

For build verification failures, send findings to the coordinator before publication. The coordinator may send actionable in-scope fixes back to the builder; the verifier rechecks each changed fix and refreshed acceptance evidence. Stop repeating the same failed fix when a missing dependency/product decision blocks progress, retain the current useful work and report the unmet criterion. Out-of-scope follow-ups may be ticketed without expanding the build. Do not leave fixable authorized work unfinished merely because it can be ticketed.

Prepare a ranked queue and reserves: in plan-only mode, supported improvement proposals; in build mode, unresolved defects and substantive deferred follow-ups. Do not create work tickets for already completed changes merely to record activity. Draft each candidate with title, problem/impact, source evidence/baseline, finding/proposal and run IDs, proposed solution, testable acceptance criteria, and suggested offline verification. Label estimates and proposed tests accurately.

### Jira publication

Use MCP first. The coordinator checks the current tool catalog for Jira/Atlassian tools and, when available, uses tool discovery to load the relevant server tools before delegating publication. When native tools are missing, use the tested local Atlassian MCP bridge through direct stdio before declaring Jira unavailable or requesting a reload. Read [the Jira MCP access reference](references/jira-mcp-access.md) for its commands, schema discovery, safe payload passing, and connection diagnostics. Record the connection/tool names and bridge/helper paths and pass them to the writer; a child may have a different tool catalog, so it must check its own access. If only the coordinator has MCP access, it executes the independently verified writer's payload using the same snapshot checks and durable ledger; this is not a new review team or an additional attempt budget.

Distinguish tool availability, configured connection, authentication, and project permissions. Missing tools do not prove expired authentication. For local Codex, `codex mcp list` can diagnose configured servers without printing credentials; `auth_status: unsupported` for this stdio bridge is not proof of failed authentication. A successful handshake/tool list proves connection, while project metadata proves the needed Jira access. MCP resource lists are not a tool catalog and an empty resource list does not establish that Jira is unavailable. If both native tools and the local bridge are unavailable or fail, preserve drafts and report the concrete connection failure. Do not automatically replace MCP with a separate browser login. Browser fallback applies only when the user requests it or MCP is confirmed unusable and the user accepts that fallback. Never request tokens/passwords in chat or read credential stores.

The coordinator saves the verified report and candidate payloads before publishing, and checks source against the verified snapshot. If scoped source changes, revalidate affected findings/proposals, save refreshed drafts and recheck the snapshot before resuming. The fourth agent owns publication payloads; the coordinator may execute them when MCP is exposed only to the coordinator, as described above.

- If writes are disabled or the queue is empty, return drafts or zero-ticket outcome without mutations; empty queues need no login.
- Use authenticated Jira MCP tools, including direct stdio through the documented local bridge, under the connection checks above; use the browser only under the fallback conditions above and after reading the `agent-browser` skill's current CLI workflow. Live Jira metadata, duplicate checks and authorized publication are part of this workflow, separate from the prohibition on live financial-provider/model calls in tests. Verify site/project, create permission, issue types, required fields and priority values from live metadata/UI. Use a supported enhancement/task type for proposals and Bug for defects where available; never invent IDs or priorities. Missing access/fields preserve drafts and block publication only, not independent authorized implementation. Never request credentials in chat.
- Search the project, including closed issues and this run's prior attempts, before each create. Compare actual root cause/outcome/component, not just titles. Record matching keys/URLs as duplicate-skipped, do not modify existing issues or recreate resolved work automatically, and use ranked reserves if appropriate. Failed duplicate checks stop writes.
- Before every create call, send the intended payload and item IDs to the coordinator. It checks the scoped snapshot again before authorizing each individual create, including later tickets in the batch. Changed evidence invalidates the proposed payload until the verifier revalidates it and the coordinator saves refreshed drafts. Once current, the coordinator durably saves the next attempt number, timestamp, payload, run/item IDs and `pending` disposition in the report, and acknowledges it. Create only after acknowledgment, sequentially, within the remaining five-attempt budget. Send confirmed key/URL immediately so the coordinator records the result before another attempt. Include sufficient evidence in Jira itself; a local report path is not accessible to a remote reader. Exclude secrets from descriptions and errors.
- Never blindly retry create failures/timeouts. Search run/item IDs and matching evidence to reconcile uncertain outcomes. Confirm an existing key or mark uncertain and stop writes. Other create failures also stop writes and preserve drafts. On resume, count every durable ledger entry, including pending/failed/uncertain; unresolved entries block writes. Missing/corrupted ledger permits drafts only, not a reset budget.
- Return per-item status (`created`, `duplicate-skipped`, `draft-only`, `blocked`, `failed`, `uncertain`), verified keys/URLs, total attempts and remaining candidates. Never claim Jira success without a verified key.

## Coordinator: handoff

Save final implementation/plan status, independent findings and verification, unmet criteria, Jira outcomes and ledger. Report what changed or was proposed, why, what was tested and not tested, report path, and confirmed ticket links/count. Label unverified or incomplete work explicitly. Preserve current test inventory unless a fresh full-suite inventory was actually measured. Creating/validating this skill is documentation work, not app delivery or live Jira execution.
